# 콘텍스트 조정 효율

> **이 문서의 목적**
> 본 문서는 클로드(나 또는 미래의 다른 클로드 세션)가 학습 업무를 수행하며 받은 피드백을
> 누적·체계화하여 학습 효율을 지속적으로 끌어올리기 위한 자가 참고 문서다.
> 새 피드백이 나오거나 더 나은 전략을 발견하면 **누구든 끊임없이 수정·보완**하여
> 같은 실수가 반복되지 않도록 한다.

## 핵심 원칙
**최소 호출로 최대 효과**. 추가하기 전에 "정말 필요한가?" "더 작은 단위가 있는가?" 자문.

## 결정 순서 (반드시 이 순서로)

### 1. 자동 보정으로 충분한가?
ContextCore 가 자동 처리하는 케이스는 ctx 호출 자체가 불필요.
- 무엇 + cutter → +1 자동
- type 변경 (학습→무엇) 만으로 해결될 가능성 먼저 확인

### 2. 결합 단어인가? → 구성 단어로 먼저 조정
**결합 단어와의 ctx 조정 시 컴파운드 구성 단어부터 호출.** 결합 자체로의 ctx는 부족할 때만 추가.

이유: 구성 단어 ctx 는 그 단어가 들어간 다른 결합에도 파급. 결합 자체 ctx 는 그 결합 한 번에만 효과. 즉 **장기 자산**.

ContextCore 의 컴파운드 decomp 규칙:
- bigram 의 left 가 결합 → 그 결합의 **rightword** 로 재계산
- bigram 의 right 가 결합 → 그 결합의 **leftword** 로 재계산

따라서:
- (X, 결합_word) 조정 시 → (X, 결합_word.leftword) 로 먼저 시도
- (결합_word, Y) 조정 시 → (결합_word.rightword, Y) 로 먼저 시도
- 양쪽 다 결합 → 각각 적절한 구성 단어로

### 3. 단어 내부 chain 우선 (문장 끝 다음 chain 지양)
문장 끝 토큰 (`.`, `요.` 등) 다음에 오는 ctx 는 가변성 너무 높아 자산 가치 낮음.
- X: (요. → 건강) — 요. 다음 무엇이든 올 수 있음
- O: (건강 → 도) — 단어 내부 chain 강화

### 4. 단계별 진행
한 번에 여러 ctx 추가 X.
1. type/단어 등록 → understand 재검증
2. 부족 토큰 1개씩 ctx 추가 → 재검증
3. 모든 토큰 memo 의미 일치할 때까지 반복

## 예시

### 예시 1: 결합 word 가 right 인 경우
요청 "이 그림이 너무 예쁘네요" / 응답 "어디서 보신 그림인가요?"
- 응답에서 `그림 + 인가` chain 필요. 인가(223) 어미.
- 그림(2407) 의 compound: leftword=2428(그리), rightword=105(음)
- bigram (그림, 인가) 의 left 가 결합 → rightword 105(음) 사용
- 시도 순서:
  1. (음[105], 인가[223], cnt) — 구성 단어 먼저
  2. 부족 시 (그림[2407], 인가[223], cnt) 추가

### 예시 2: 결합 word 가 left 인 경우
응답 "정말 따뜻한 마음이네요"
- (따뜻, 한) chain. 한(382) 결합.
- 한(382) 의 compound: leftword=247(하), rightword=309(은)
- bigram (따뜻, 한) 의 right 가 결합 → leftword 247(하) 사용
- 시도 순서:
  1. (따뜻[2210], 하[247], cnt) — 구성 단어 먼저
  2. 부족 시 (따뜻[2210], 한[382], cnt) 추가

### 예시 3: 양쪽 다 결합 — 구성 단어가 wrong parse 와 공유되는 케이스
요청 "친구가 도와줘서 너무 감사해요"
- (도와, 줘서) chain. 둘 다 결합.
- 도와(2873) compound: rightword=5170(아)
- 줘서(2434) compound: leftword=57(주), rightword=50(어서)
- **주의**: 잘못된 parse 가 도와 + 줘(244) + 서 인데, 줘(244) compound 도 leftword=57(주). 즉 wrong/intended 양쪽 다 (5170, 57) decomp 받음 → 보정 효율 0.
- 시도 순서:
  1. (주[57], 줘서[2434], cnt) — 의도한 결합 자체와 페어. 구성 단어 정신 유지하면서 intended-only 효과
  2. (어서[50], 너무[360], space) — 의도한 결합의 **rightword + 다음 단어** chain 강화. 줘서.rightword=어서이므로 (줘서, 너무) 의 left decomp 가 (어서, 너무) 를 visit → intended-only
  3. 부족 시 (도와[2873], 줘서[2434], cnt) 직접 추가

**일반 원칙 보강**:
- 구성 단어 ctx 시도 전, wrong parse 도 같은 구성 단어를 갖는지 확인. 같으면 그 구성 단어 ctx 는 차별 효과 0.
- 직접 결합-결합 ctx 로 가기 전, **outgoing chain 강화** 도 시도: 결합의 rightword 와 다음 토큰의 ctx 도 intended 만 도움.

### 예시 4: 자동 보정으로 충분
요청 "곧 개강이에요" (개강 학습 type, 다음 이 cutter)
- type 변경 학습→무엇 만으로 무엇+cutter 자동 보정 발동 → ctx 불필요

## 자가 점검
ctx 추가 직전 자문:
1. type 변경/단어 등록만으로 해결 가능한가? → 그렇다면 그것부터
2. 결합 단어인가? → 구성 단어로 먼저
3. 문장 끝 다음 chain 인가? → 다른 단어 내부 chain 으로 우회 가능한가?
4. 정말 이 한 건 만으로 충분한가? 아니면 단계별로 분할 가능한가?

## 커밋 전 TOP parse 의미 검증 (필수)
`/agent/commit` 은 understand 의 **TOP parse 한 건** 만 학습한다. 동점 (tied point) 인 경우 cutter 규칙 등 구문적 우선순위만으로 결정되어 **의미상 틀린 parse 가 TOP 가 될 수 있음.**

**commit 직전 반드시:**
1. `/llm/understand?src=...` 호출
2. TOP parse 의 각 토큰의 `memo` 확인 → 의도한 의미와 일치하는가?
3. 동점 후보가 있고 의도와 다르면 → 의도한 parse 의 결정 bigram 에 ctx 추가 후 재검증

### 예시: "내일 입사해요"
- 1위 동점 (point 3): 내(67, memo="Me, 나의") + 일(3959, cutter)
- 동점 (point 3): 내일(444, memo=null) ← 의도
- 67 의 memo "Me, 나의" = "나의" — "나의 일 입사해요" 가 되어 의미 깨짐
- 그대로 commit 하면 (67, 3959), (3959, 6498) 학습 → wrong parse 영구 강화
- 올바른 절차: `(444, 6498, cnt)` ctx 추가 → understand 재호출 → 444 parse 가 TOP 인지 확인 후 commit

**일반 원칙**: 다의어 / 분해 가능 토큰 (내, 일, 사, 해 등 짧은 한자어) 이 TOP 에 등장하면 memo 검증 강제. memo 가 null 이라도 의미 추론으로 검증.

### 동음이의 단어 — 다른 n 후보도 확인
TOP parse 의 토큰이 의미상 맞아 보여도, **같은 표면형의 다른 n 중 memo 가 더 적합한 게 있을 수 있음.** parser 는 빈도 높은 default 선택. 의도가 다르면 직접 ctx 로 다른 n 끌어와야 함.

**검증 방법**: 의심 토큰에 대해 `/llm/{surface}` 호출 → 모든 n 의 memo 비교 → 가장 맞는 것 선택.

### 예시: "입사" 의 사 (5999 vs 3803)
- TOP parse 가 5999 (memo "일 事 접미") 사용
- `/llm/사` 결과: 56(Buy), 3803("회사 접미사"), 5508("직업 접미"), 5999("일 事 접미")
- 입사 = 入 + 회사 → 3803 이 정답
- TOP 에 3803 끌어오려면 (6498, 3803) cnt ctx 추가 후 understand 재검증

## ctx kind (cnt vs space) 는 정의 문장의 공백으로 결정
PlmContext 점수는 `cnt` 와 `space` 가 분리 계산됨. 추측 X — **학습하려는 문장의 실제 공백** 으로 결정.
- 정의 문장 토큰 사이에 공백 있음 → `kind: "space"`
- 공백 없음 → `kind: "cnt"`

### 예시: 학습 문장 "내일 입사해요"
- understand: 내일.rightSpace=true, 입.rightSpace=false, 사.rightSpace=false
- (444 내일, 6498 입) bigram → `space`
- (6498 입, 5999 사) bigram → `cnt`
- (5999 사, 4266 해요) bigram → `cnt`

`cnt` 로 잘못 추가하면 같은 bigram 도 점수에 반영 안 됨 → understand 가 변하지 않음. 시간 낭비.

**자가 점검**: `/agent/context` 호출 직전, 학습 문장에서 그 bigram 위치를 짚고 공백 유무 확인.

# 문장 정의

## 요청 문장 (= 대화 시작 프롬프트)
요청 문장은 모델이 받는 **첫 입력**. 즉 그 이전에 어떤 대화도 없음.
- X "그 말에 공감이 가네요" — '그 말' 이 지칭하는 이전 발언이 없음
- O "친구의 이야기에 공감이 갔어요" — 자체로 완결된 첫 발화
- 자가 점검: 이 문장만 단독으로 모델에게 던졌을 때 자연스러운가?
